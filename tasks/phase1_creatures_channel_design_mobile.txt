2. 環境制約の確認結果
================================================================

■ メモリ: WSL2 割当 5.7GB (使用 1.1GB / 空き 4.5GB)
  video_build が 2〜3GB 使う
  → 2本並列は OOM 確定
  → 直列必須

■ ディスク: C: 238GB中 123GB空き + 7日自動削除
  → 問題なし

■ Gemini API: 2.5 Pro 無料枠内
  → 2本/日なら余裕、時差起動推奨

■ YouTube OAuth: credentials.json + token.json 1組
  → 最大の構造変更点、別 token 必須

■ Task Scheduler: YukkuriDaily 1本 (10:00)
  → 別 URI で新規登録可能、既存壊さない

4. 実行スケジュール (直列+時差)
================================================================

10:00  健康チャンネル (既存 YukkuriDaily)
12:00  生物チャンネル (新規 CreatureDaily)
13:00  両チャンネル プリフライト

■ 重要な変更
健康側の3回リトライは最悪 11:50 頃まで続く可能性
→ 生物側は当初案 11:30 ではなく **12:00 起動** を推奨

■ 並列禁止の理由
- skill_video_build で ffmpeg が 2〜3GB 消費 → OOM 確定
- Gemini 2.5 Pro 同時呼び出しで RPM 逼迫
- 失敗時のログ追跡困難

■ 連動失敗ガード
- run_creatures.bat 冒頭で健康側の当日完了を確認
- 生物側が失敗しても健康側は影響を受けない設計
- lock file と run_dir は完全独立

8. 懸念点・リスク トップ10
================================================================

1. 認証情報の取り違え (最重要)
   → skill_upload 冒頭で channels().list(mine=True) を呼び
     expected_channel_id と不一致なら fail-closed
   → metadata.json にも channel_id 記録で二重防御

2. Phase2 実装中に健康チャンネルが壊れる
   → Step1 の抽象化リファクタで既存挙動完全一致を
     Codex adversarial review で確認してから次へ
   → DRY_RUN と実投稿の両方で確認

3. prompts.py 分割時にナラティブスタイル文言が破損
   → ファイル移動のみ、文言変更ゼロ
   → 互換 re-export で import 文変更不要

4. 生物台本が5幕17分になり既存文字数閾値と不整合
   → channel config で閾値上書き可能にする

5. Wikimedia ライセンス欠損
   → skill_credits がライセンス情報必須フィールド化
   → 欠損時は該当画像破棄 + 全破棄なら台本中断

6. 11:30 起動が健康側リトライと衝突
   → 12:00 起動に変更を推奨

7. 1日1本ルールの合算誤動作
   → channel 別 lock_file で独立
   → YouTube API 側も forMine=True で自動分離

8. preflight 13:00 実行時に片方だけ失敗した場合
   → 両チャンネル独立に修復
   → 片方失敗でも他方のアップロードをブロックしない

9. Discord 通知のチャンネル識別
   → 通知文先頭に [health]/[creatures] プレフィックス必須

10. 3チャンネル以上への拡張時のテスト負担
    → Phase2 で smoke test を新設
